## 3. 存量问题详细分析(影响场景 + 修复建议)

> 以下 18 项未修复项按修复优先级给出落地建议;详细机制分析可对照 2026-07-19 审计原文。

### 🔴 P0-1 网络 sink 持锁无限阻塞 —— 全进程日志冻结(必修)

- **链路**:`hx_core_emit_to_sinks()`(core.c:1132-1152)持递归 `sink_lock` 逐 sink 写 → `net_write()`(net.c:163)→ TCP 分支 `send()`(net.c:196)在**阻塞 socket**(net.c:106 连接后切回阻塞)上循环写。`connect` 用 `select` 限了 2s(net.c:69-108),但**稳态 send 没有任何超时**。
- **触发**:采集端 TCP 窗口塞满后停止读(宕机但不断链、网络分区)。同步模式:所有业务线程在 `sink_lock` 上排队;`flush`/`remove_sink`/`shutdown` 全部同锁死锁。异步模式:worker 卡在 send,队列打满后 BLOCK 策略反压生产者 —— 表现仍是全进程日志冻结。

## 4. 专题:Windows"为什么内存损坏时拿不到 dump"

### 4.1 终止路径分类(机制)

Windows 进程终止有多条互不相同的通道,**能否生成 dump 取决于终止走哪条通道**:

| 通道 | 机制 | 进程内 handler 可见? |
| --- | --- | --- |
| **SEH 未处理异常**(访问违例、除零、非法指令…) | 二次机会异常派发 → `SetUnhandledExceptionFilter` → WER | ✅ UEF 被调用 |
| **`abort()`/SIGABRT** | UCRT `raise(SIGABRT)` → 无 handler 则直接退出码 3 | ❌ 不产生任何 SEH 派发 |
| **C++ 纯虚调用** | `_purecall` → 默认直接终止 | ❌ 同上 |
| **CRT 无效参数**(release UCRT) | `_invalid_parameter` 默认 → `__fastfail(FAST_FAIL_INVALID_ARG)` | ❌ fast-fail 绕过 SEH |
| **堆元数据损坏**(Win8+) | ntdll `RtlReportCriticalFailure` → fail-fast 终止 | ❌ fast-fail 绕过 SEH(部分旧路径以 0xC0000374 异常形式可达 UEF,但见 4.2 第 2 层) |
| **`/GS` 栈 cookie 破坏** | `__report_gsfailure` → `__fastfail(FAST_FAIL_STACK_COOKIE_CHECK_FAILURE)` | ❌ fast-fail 绕过 SEH |
| **`TerminateProcess`/`ExitProcess`/挂死** | 直接终止/无终止 | ❌ 任何进程内手段无效 |

**核心结论**:fast-fail(`__fastfail`/`RaiseFailFastException`)由内核直接终止进程,**不可能**被 SEH/VEH/UEF 捕获——这不是实现问题,是设计如此。因此"内存损坏(堆元数据、栈溢出写穿 cookie)时拿不到 dump"在进程内是**无解**的;唯一可靠出路是 **Windows 错误报告(WER)在进程外写 dump**(LocalDumps 机制),WER 服务本身能观测到 fast-fail 终止。

### 4.2 "拿不到 dump"的四层拆解与本次对策

1. **SEH 可达,但 dump 写不出**:崩溃线程持有堆锁(如崩溃在 `malloc` 内部)→ `MiniDumpWriteDump` 内部分配 → **死锁**;堆元数据已坏 → dbghelp 失败。旧代码失败还完全静默。
   → **对策**:重入守卫止损(N-1)+ 失败写进报告(N-6)+ **放行 WER**(N-7)让进程外兜底。
2. **fail-fast 不可达**:堆元数据/GS cookie/未接管的无效参数。
   → **对策**:无效参数类经 `_set_invalid_parameter_handler` **转为 SEH 异常**(N-4,从"零 dump"变"有 dump");堆元数据/GS cookie 进程内无解 → **WER LocalDumps 注册 API**(N-5 缓解)。
3. **不走异常的终止**:abort/纯虚。
   → **对策**:funnel 接管(N-4)。
4. **TerminateProcess/挂死**:进程内外(指本库)均无解 → 建议部署侧看门狗/`procdump -e` 监控(本报告仅建议,未实现)。

### 4.3 改造前后覆盖矩阵

| 终止路径 | 改造前 进程内 | 改造前 进程外(WER) | 改造后 进程内 | 改造后 进程外 |
| --- | :-: | :-: | :-: | :-: |
| SEH 未处理异常 | ✅ | ❌(被 `EXECUTE_HANDLER` 压制) | ✅(加固后) | ✅(放行) |
| `abort()` / SIGABRT | ❌ 零产物 | ❌ | ✅ | ✅ |
| CRT 无效参数(release) | ❌ fast-fail | 仅 WER 自身 | ✅ | ✅ |
| C++ 纯虚调用 | ❌ | ❌ | ✅(MSVC) | ✅ |
| 堆元数据损坏 / GS cookie | ❌ 不可能 | 仅 WER 自身(需 LocalDumps) | ❌ 不可能 | ✅ **LocalDumps API** |
| 进程内 dump 失败(堆锁死锁等) | ❌ 且不知情 | ❌ | ✅ 失败可见化 | ✅ |
| TerminateProcess / 挂死 | ❌ | ❌ | ❌ | ❌(需看门狗) |

### 4.4 部署注意事项(实测发现)

- **WER 被组策略禁用时**(`HKLM\SOFTWARE\Policies\...\Windows Error Reporting\Disabled=1`,本机即如此):WER 仍会为崩溃写 LocalDumps,但**按应用配置的 `DumpFolder` 被忽略**,dump 落在默认 `%LOCALAPPDATA%\CrashDumps`。已写入文档。
- **error mode 继承**:宿主(某些 shell/调度器,实测 Git Bash 即如此)设置 `SEM_NOGPFAULTERRORBOX` 会被子进程继承,抑制 WER。从这类宿主启动的应用需自行 `SetErrorMode(0)`。已写入文档。
- **WER 放行的副作用**:系统"程序已停止工作"流程可能可见 —— 已做成选项(默认开,可关)。

### 4.5 WER 注册表方案的可靠性(重启 / 掉电 / 内存损坏 / 多用户)

针对"重启后或异常情况下注册表是否可靠"的专项分析;可进程内解决的三项已在本轮代码落地(见 §6):

| 场景 | 机制 | 结论 |
| --- | --- | --- |
| 重启后 | HKCU 存于用户配置单元 NTUSER.DAT,持久化 | ✅ 注册保持,无需重做;仍建议每次启动调用 enable()(幂等、自愈) |
| enable() 返回后立即掉电 | `RegCloseKey` 不保证落盘,内核惰性刷写 hive | ✅ **已加固**:返回前 `RegFlushKey` 强制刷盘 |
| enable() 执行途中崩溃 / 堆已损坏 | 注册表由内核配置管理器写入,用户态堆损坏**不可能**破坏 hive;值经拷贝传递,非用户缓冲直写 | ✅ 最坏是调用失败并返回错误码 |
| 三个值只写了一部分 | 值按重要性排序写入(DumpFolder→DumpType→DumpCount);WER 对缺失值用文档默认(DumpType→minidump、DumpCount→10) | ✅ 优雅降级:仍产出 dump,且落在已写入的 DumpFolder |
| 崩溃时 DumpFolder 目录不存在 | WER 对缺失目录可能**静默跳过**(无 dump 且无提示) | ✅ **已加固**:enable() 提前创建绝对路径目录 |
| 崩溃瞬间机器硬断电 | WER 正在写的 .dmp 可能截断 | ⚠️ 任何崩溃时产物的固有限制,与注册表无关 |
| Windows 服务(SYSTEM/其他账户) | HKCU 按用户隔离;服务的 HKCU 是服务账户的 hive | ⚠️ 需在服务账户下注册,或用 HKLM(需管理员,建议部署侧完成,文档已注明) |
| 两个不同应用 exe 同名 | 按应用键以可执行文件**名**匹配,不含路径 | ⚠️ 共用一份注册(LocalDumps 机制如此),需命名区分,文档已注明 |
| 注册表清理工具 / 配置文件重置 | 外部删除 | ⚠️ 每次启动重调 enable() 自愈(推荐,文档已注明) |

核心结论:**注册表本身由内核写入与持久化,进程内内存损坏不可能损坏它**——"内存损坏导致注册表坏掉进而拿不到 dump"这条链路不成立;真正会丢注册的是"惰性刷写 + 掉电"与"目录不存在"两个窗口,均已用 `RegFlushKey` + 提前建目录关闭。

## P0

### P0-1 TCP 对端停读时，阻塞 `send()` 在持有 `sink_lock` 期间无限期挂起，全进程日志冻结

- **位置**：`src/hx_clog_net.c:196`（send 循环）；`src/hx_clog_net.c:106`（连接成功后 `net_set_blocking(fd, 1)` 恢复阻塞模式）；调用点 `src/hx_clog_core.c:1130-1149`（`hx_core_emit_to_sinks` 全程持有 `sink_lock`）。
- **缺陷**：连接阶段做了有界超时（非阻塞 + `select` 2s），但稳态发送把 socket 切回阻塞模式且从不设置 `SO_SNDTIMEO`，`send()` 无任何超时保护。
- **失败场景**：采集端接受了连接但停止读取（GC 停顿、磁盘满、half-open 且不发 RST——对端"活着"，TCP 永远不报错）。内核发送缓冲填满（约 64 KB–2 MB）后 `send()` 无限期阻塞：
  - 同步模式（默认）：日志线程持有 `sink_lock` 挂死，其它所有日志线程、`hx_clog_flush`、`hx_clog_remove_sink`、`hx_clog_shutdown` 全部永久阻塞。
  - 异步模式：worker 在 `src/hx_clog_async.c:305` 挂死，队列填满后 `HX_CLOG_OVERFLOW_BLOCK` 策略下所有生产者线程也阻塞——同样是全进程日志冻结。
- **建议**：设置 `SO_SNDTIMEO`，或保持 socket 非阻塞并像 connect 路径一样做有界等待；超时按链路故障处理（断连 + 退避 + 上报）。文件头注释"异步队列在上游提供真正的缓冲"（`net.c:9-11`）在 worker 自身被卡死时不成立。

## P1

### P1-1 `hx_clog_init_locked` 不持 `sink_lock` 改写 sink 列表与格式状态

- **位置**：`src/hx_clog_core.c:1444-1486`。
- **缺陷**：init 只持有 `init_lock`，就直接写 `g_core.pattern`、`format_mode`、`formatter`、`sink_count = 0` 并调用 `add_sink()`；而同一状态的其它所有写者（`hx_clog_set_pattern`、`hx_clog_add_callback_sink_ex`、`hx_clog_reconfigure_locked`、`hx_clog_shutdown`）都正确持有 `sink_lock`。
- **失败场景**：线程 A 执行 `hx_clog_init()` 的同时线程 B 调用 `hx_clog_add_callback_sink_ex()` 或 `hx_clog_set_pattern()`（两者在 init 前后调用都是合法的，只要求 `ensure_once()`）。B 持锁、A 不持锁，双方并发写 `g_core.sinks[]`/`sink_count`/`pattern`：sink 注册可能丢失、数组同下标被双写损坏，`fmt_cache_refresh()` 可能读到写了一半的 pattern。`reconfigure` 已按 CLAUDE.md 的规则在 `sink_lock` 下做交换，init 漏掉了同样的处理。
- **建议**：`hx_clog_init_locked` 中对 sink 列表与格式字段的改写整体纳入 `sink_lock`（该锁是递归锁，与 init 内部对 `add_sink` 的调用兼容）。

### P1-2 网络 sink 写路径在 `sink_lock` 下内联执行无界 DNS 解析 + 2s connect

- **位置**：`src/hx_clog_net.c:118`（`getaddrinfo`）、`:140`（connect，2000 ms），由 `net_write`（`:173`）在每个重试窗口触发。
- **失败场景**：采集端宕机或 DNS 变慢时，同步模式下每 2 秒（`HX_NET_RETRY_SECS`）就有一次日志调用在 `sink_lock` 下停顿"DNS 超时（5–30 s，不可控）+ 2 s"——期间全进程所有日志线程一起停顿，且周期性重复。异步模式下同样周期性拖慢 worker。
- **建议**：至少将解析/重连移出热路径（专用重连线程或在 worker 空闲时做）；短期缓解可缓存解析结果、拉长退避。文件头"添加 sink 永不阻塞"的说法对写路径不成立。

### P1-3 POSIX 下 `FD_SET` 对 fd ≥ `FD_SETSIZE` 无检查 → 栈越界写

- **位置**：`src/hx_clog_net.c:90-94`。
- **缺陷**：`net_connect_tcp()` 直接 `FD_SET(fd, &wset)` / `select(fd+1, …)`，未验证 `fd < FD_SETSIZE`（Linux 上为 1024）。
- **失败场景**：持有 >1024 个描述符的服务进程（恰是需要网络日志 sink 的那类应用）中，惰性建连拿到 fd ≥ 1024，`FD_SET` 越界写栈上 `fd_set` —— 日志库内部的栈内存损坏，或在 glibc `_FORTIFY_SOURCE=2` 下直接 abort。Windows 不受影响（其 `fd_set` 是 SOCKET 数组）。
- **建议**：改用 `poll()` / `WSAPoll()`。

### P1-4 INI 解析器把未校验的 `atoi` 结果送进异步队列容量 → 32 位平台堆损坏

- **位置**：`src/hx_clog_core.c:1029-1034`（`cfg->async_queue_size = (unsigned int)atoi(v);` 等）；下游 `src/hx_clog_async.c:101`（`hx_clog__malloc(sizeof(async_slot_t) * cap)`，无上限、无溢出检查）。
- **失败场景**：配置文件写 `async_queue_size=-1`（或任何 > `SIZE_MAX/sizeof(async_slot_t)` 的值）→ `cap = 4294967295`。32 位目标上乘法在 `size_t` 中回绕，malloc 成功但缓冲极小，而 `g_async.capacity` 仍为 42 亿，生产者按 `slots[(head+count) % capacity]` 索引远超分配区 —— 静默堆损坏。64 位上是约 100+ GB 的分配失败、静默降级为同步模式。乘法本身早于本次改动，但 INI 加载器让文本文件里的垃圾/负值第一次变得可达。
- **建议**：在 `ini_apply_kv` 中做范围钳制并对非法值调用 `hx_core_report_error`；`async_batch_size`、`flush_interval_ms`、`rotate_interval_seconds` 同理（`rotate_interval_seconds=-1` 会变成约 136 年的间隔，静默禁用时间轮转）。`hx_async_start` 侧也应加乘法溢出防护做纵深防御。

### P1-5 atexit flush 无界等待异步 worker → `ExitProcess`/DLL 卸载时进程退出挂死

- **位置**：`src/hx_clog_core.c:1414`（`hx_atexit_flush`，`:1504` 注册）；`src/hx_clog_async.c:331-336`（`hx_async_flush` 以 100 ms 条件等待循环直到 `count == 0`，对 worker 存活无任何检查）。
- **失败场景**：共享库构建（`HX_CLOG_BUILD_SHARED=ON` 是一等配置）下，任何代码调用 `ExitProcess()` 会先终止其它所有线程，然后在 loader lock 下的 `DLL_PROCESS_DETACH` 期间跑 CRT atexit 表。此时 async worker 已死、`g_async.count > 0`、`running` 仍为 1 —— `hx_async_flush` 永久自旋，进程挂死在 DllMain 里。更早一步，`dup_flush_pending()`（`core.c:1539`）要拿 `g_err_lock`/`g_dup.lock`，也可能被已终止线程遗留持有。
- **建议**：atexit 钩子跳过排空（只 flush 各 sink 的已写数据），或给等待加上限并检查 worker 存活。

### P1-6 头文件版本宏未随 1.3.0 发布升级

- **位置**：`include/hx_clog.h:45-47`（`HX_CLOG_VERSION_MINOR` 仍为 `2`）；对照 `CMakeLists.txt:4`（`VERSION 1.3.0`）、`cmake/hx_clog.pc.in`、ConfigVersion 文件与 `CHANGELOG.md` 的 `[1.3.0]` 条目。
- **失败场景**：按文档惯例做 `#if HX_CLOG_VERSION_MINOR >= 3` 特性检测的使用者会静默编译走回退路径（明明注册表/网络 API 都存在）；包管理器看到安装包内头文件自称 1.2.0 而包版本是 1.3.0。发布提交 `c8be22f` 声称的"version bump"只落在了 CMake。
- **建议**：升宏到 1/3/0，并在发布清单/CI 中加一致性检查（头文件宏 == `PROJECT_VERSION`）。

## P2

### P2-1 `HX_LOG_*_EVERY_N(0, …)` 整数除零；计数器并发自增是正式数据竞争

- **位置**：`include/hx_clog.h:513, 527, 541, 555, 569, 583`（`(hx_clog_n_++ % (unsigned long)(n)) == 0`）。
- **场景**：(a) 运行时算出的 `n` 为 0（如一个可配置的采样步长归零）→ 除零 UB，x86 上 SIGFPE。(b) `static unsigned long hx_clog_n_` 的无同步 RMW 在 C11/C++11 内存模型下是未定义行为而非"不精确"；本项目自身以 TSan 为发布门槛，用户代码在两个线程调用同一 `EVERY_N` 站点跑 TSan 必报竞争且指向本库头文件。
- **建议**：`((n) ? (unsigned long)(n) : 1UL)` 防除零；计数器在 C11/C++11 可用时用宽松原子（`_Atomic`/`std::atomic`），仅对前 C11 编译器回退普通 static。

### P2-2 UDP 超大报文（`EMSGSIZE`）被当作链路故障，且 UDP 丢失完全静默

- **位置**：`src/hx_clog_net.c:182-188`。
- **场景**：行上限默认 512 KB 而 UDP 报文上限约 65507 字节；一条大行导致 `sendto` 失败，代码调用 `net_disconnect()` 并进入 2 s 退避——后续正常大小的行被丢弃 2 s，恢复时还要重新走 DNS。且该失败路径从不调用 `hx_core_report_error`，与文件头"drops are reported… at most once per retry window"（`net.c:10-11`）矛盾——UDP 丢失完全无声。
- **建议**：`EMSGSIZE` 只丢当前行、不拆连接状态；UDP 失败按注释承诺的频率上报。

### P2-3 `hx_clog_reconfigure` 永久且静默地销毁网络 sink

- **位置**：`src/hx_clog_core.c:1366-1383`（`close_non_callback_sinks_locked` 关闭包括 NETWORK 在内的所有非回调 sink）；重建逻辑只覆盖 console/file/system sink。
- **场景**：应用通过 `hx_clog_add_network_sink()` 加了 TCP sink，之后仅为改 level 或换目录调用一次 `hx_clog_reconfigure()` → 远程日志永久停止，无错误上报，且 config/INI 中没有任何字段能表达网络 sink、无法重建。回调 sink 被刻意保留，新 sink 类型两头都没顾上。
- **建议**：让网络 sink 像回调 sink 一样跨 reconfigure 存活，或在 config/INI 中加入网络 sink 字段；至少在文档中写明并上报。

### P2-4 fork 后父子进程共享同一条 TCP 连接；全库无 `SOCK_CLOEXEC`

- **位置**：`src/hx_clog_core.c:2041-2045`（`hx_clog_after_fork_child` 只重开文件 sink、重启 async，未处理网络 sink）。
- **场景**：POSIX fork 后父子都对同一 TCP 流 `send()`，配合部分写循环（`net.c:195-206`），两个进程的字节可在行中间交错 → 采集端收到损坏的行。另外整个 `src/` 无任何 CLOEXEC 设置，fork+exec 的子进程会一直占着采集端连接。
- **建议**：`hx_clog_after_fork_child` 中对网络 sink 调 `net_disconnect`（惰性重连兜底），与文件 sink 重开保持对称；建 socket 时设置 `SOCK_CLOEXEC`/`FD_CLOEXEC`（Windows 对应 `WSA_FLAG_NO_HANDLE_INHERIT`）。

### P2-5 重连退避使用墙钟；`EINTR` 被当作致命错误

- **位置**：`src/hx_clog_net.c:168-169`（`time(NULL)` 退避基准）；`:94-96`（`select` 被信号打断即放弃可能已成功的连接）；`:196-204`（`send` 返回 −1/EINTR 即丢行、断连、进退避）。
- **场景**：NTP 时钟回拨 1 小时 → `now - last_attempt_sec` 为负且持续 < 2，重连被禁用 1 小时（该 sink 完全无输出）。SIGPROF 类采样分析器下会出现偶发的假断连、丢行与错误处理器抖动。
- **建议**：退避改用单调时钟（核心已有时间抽象）；`EINTR` 重试。

### P2-6 pre-init 添加的网络 sink 被 init 泄漏（含 Windows winsock 引用计数）

- **位置**：`src/hx_clog_core.c:1451`（`init_locked` 直接 `sink_count = 0`，不关闭既有 sink）；`src/hx_clog_net.c:247`（创建时 `WSAStartup`）与 `:227`（仅 `net_close` 里 `WSACleanup` 配平）。
- **场景**：`hx_clog_add_network_sink` 在 `hx_clog_init` 之前调用是可行的（只依赖 `ensure_once`），但随后的 init 把 sink 表清零而不关闭旧 sink —— 泄漏 sink 结构体，Windows 上还泄漏一次 WSAStartup 引用。"必须在 init 之后添加"的惯例目前只对回调 sink 有文档。
- **建议**：init 清表前先关闭非回调 sink，或在头文件为网络 sink 补上同样的时序契约。

### P2-7 logger 注册表：超长名字存储截断但查找用全名比较 → 无界泄漏与碰撞

- **位置**：`src/hx_clog_core.c:2569`（`logger_find_locked` 用 `strcmp` 比较完整调用方名字）；`:2611`（`strncpy(lg->name, name, sizeof(lg->name)-1)` 截断到 127 字节存储）。
- **场景**：任何 ≥128 字符的名字（深层点分层级或自动生成的名字很容易达到）查找永远匹配不上之前存的截断条目，于是每次 `hx_clog_logger_get("同一个长名")` 都新分配并注册一个 logger —— 长期运行、按日志站点调用 `logger_get` 的进程内存无界增长。另外两个前 127 字符相同的不同长名会在 `hx_clog_logger_find` 中静默碰撞。
- **建议**：查找键按同样规则截断后再比较，或直接拒绝超长名字并上报。

### P2-8 `hx_clog_logger_drop_all` 释放其它线程可能正在使用的 logger

- **位置**：`src/hx_clog_core.c:2672-2685`；使用点 `:2716-2717`（`hx_clog_logger_writev` 把 `actual->name`、`&actual->level` 传入 `core_writev`）。
- **场景**：线程 A 缓存了 `hx_clog_logger_get` 返回的指针（这正是预期用法）并在 `core_writev` 中解引用时，线程 B 调用 `hx_clog_logger_drop_all()` → use-after-free。头文件写了"valid until drop_all"，但没有任何机制（引用计数/静默期/使用警告）让多线程程序能在非完全停机时安全调用它。
- **建议**：至少在头文件写明"仅当确认无其它线程还会通过注册表指针记日志时才可调用"；理想方案是延迟回收。

### P2-9 `hx_clog_get_config` 返回的字符串指针与 `level` 字段均有并发/新鲜度问题

- **位置**：`src/hx_clog_core.c:1800-1815`；`store_active_config_locked` `:1388-1391`。
- **场景**：(a) 结构体拷贝在 `init_lock` 下完成，但字符串字段指向 `g_core.cfg_*` 缓冲区，调用方解锁后解引用会与并发 `hx_clog_reconfigure` 的 `strncpy` 竞争（撕裂读），调用方无任何手段同步。(b) `level` 只在 init/reconfigure 时快照，之后的 `hx_clog_set_level()` 不反映 —— 与 `:1390-1391` 注释声称的"快照反映实时状态"矛盾。(c) 文档推荐的 `get_config → 修改 → reconfigure` 回环会让 `HX_CFG_COPY_STR` 做自别名 `strncpy`（restrict 违规，形式 UB，当前 libc 上无害）。
- **建议**：`get_config` 改为把字符串拷入调用方缓冲或库内每线程缓冲；`level` 现场原子读 `g_core.level`；`HX_CFG_COPY_STR` 加 `src != dst` 防护。

### P2-10 错误处理器在持有 `init_lock` 时被调用；处理器内调 `get_config` 在 POSIX 上自死锁

- **位置**：`src/hx_clog_core.c:525`（`hx_ring_init` 内的 `hx_core_report_error`，由 `hx_clog_init_locked:1461` 在持有 `init_lock` 时调用）。
- **场景**：`init_lock` 在 POSIX 上是普通非递归互斥量。用户错误处理器若调用新 API `hx_clog_get_config()`（`:1808` 要拿 `init_lock`）——"出错时把当前配置记下来"是很自然的写法——初始化线程在 Linux/macOS 上自死锁。违反 CLAUDE.md"不得在处理器契约不知晓的锁下调用处理器"的规则（`:1467/:1477` 是本次改动之前就存在的同型问题）。
- **建议**：先缓存消息、释放 `init_lock` 后再上报；或在头文件写明错误处理器内禁止调用哪些 API。

### P2-11 INI 解析：超长行被静默截断并可能误解析；`ini_size` 溢出静默回绕

- **位置**：`src/hx_clog_core.c:1054`（`char line[1200]`）、`:1080`（fgets 循环）；`ini_size` `:971`。
- **场景**：长于缓冲的行（长 `pattern` 或接近 `HX_CLOG_PATH_MAX` 的深路径）被 `fgets` 拆成多段：第一段被截断应用，续段被当作新行解析——若续段恰好含 `=`（长 pattern/路径中并不罕见），`=` 前的文本成了键；未知键被忽略，但形如 `...level=debug` 的尾巴会被真的应用。两种情况都无任何诊断。另外 `ini_size` 对 `max_file_size=20000000000G` 这类值静默回绕成任意小值，非数字垃圾返回 0——错误的 `max_file_size` 静默禁用或错配大小轮转。
- **建议**：缓冲读满且无 `\n` 时上报并丢弃该行余下部分；`ini_size` 做溢出检查与非法值上报。

### P2-12 JSON 格式化器不校验 UTF-8，无效字节直通 → 产出非法 JSON

- **位置**：`src/hx_clog_format.c:232-240`（`ap_json_escaped` 处理了引号/反斜杠/C0 控制字符，但 ≥0x20 的字节原样通过）。
- **场景**：消息或上下文值中含无效 UTF-8（日志参数里混进二进制、错误码页的字符串）→ JSON 行不是合法 JSON。配合新的网络 sink 送 JSON-lines 采集端时，一条坏行可能让该记录乃至整批被下游拒收。
- **建议**：对无效序列输出 U+FFFD（替换字符），保持行始终为合法 JSON。

### P2-13 `hx_clog_set_crash_callback` 依赖普通存储的写入顺序

- **位置**：`src/hx_clog_core.c:1183-1190`。
- **场景**："先设 ud 再设 cb，使并发崩溃不会看到新 cb + 旧 user_data"的方案用的是三个普通非原子存储；编译器与弱序 CPU 可自由重排，恰好破坏其声明的不变式。线程 A 调 `set_crash_callback(cb2, ud2)` 时线程 B 崩溃 → 信号处理器可能以旧 `ud1` 调用 `cb2`。
- **建议**：用现成的 `hx_atomic_*` 做 release/acquire 配对，或换成单个指针指向 {cb, ud} 结构体的原子交换。

### P2-14 C11 原子回退分支把 `volatile int*` 强转为 `volatile _Atomic int*`

- **位置**：`src/hx_clog_core.c:255-256, 265-266`。
- **场景**：被操作对象（`g_core.level`、`logger->level`、`g_dup.enabled`）声明为普通 `int`/`volatile int` 而非 `_Atomic int`；C11 允许 `_Atomic int` 与 `int` 有不同的大小/对齐/表示，这个强转恰在该分支所服务的"非 GCC/非 MSVC 编译器"上是未定义的。实际风险低（主流 ABI 二者一致），但该分支存在的唯一目的就是这类编译器上的正确性。
- **建议**：把对象本身声明为 `atomic_int`（藏在抽象后），或在注释中明确该分支为 best-effort。
